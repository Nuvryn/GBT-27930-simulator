# 项目开发流程

本项目采用适合个人开发者的简化分支流程：

```text
main → feature/<功能名> → 测试、审查 → 合并回 main → 按需打标签发布
```

## 分支与开发

- `main` 为稳定主分支，保持可构建、可验证；其最新提交不一定已经正式发布。
- 功能开发、缺陷修复及文档规范更新，均从最新的 `main` 创建独立的 `feature/<功能名>` 分支，例如 `feature/ui`、`feature/log-retention`。
- 同一功能的编辑、必要格式化、文档和测试调整在同一分支完成。按完整功能、独立修复或有意义的已验证阶段提交，不要求每次小改动都提交。
- 不设置长期 `develop`、`release` 或专用 `hotfix` 分支。已发布版本的问题也通过独立功能分支修复。

## 验证与合并

合并前检查差异，确认没有无关修改、临时文件或敏感信息，并完成与改动相符的测试及审查。个人开发可自行审查差异，不强制创建 PR；多人协作时可使用 PR 审查。

协议改动按项目测试规范回归；文档改动检查内容、链接和差异即可。缺少测试环境时记录 SKIP 及边界，不把未验证项记为通过。

验证和审查通过后合并回 `main`，完成后删除功能分支；已推送的功能分支也可在远程清理。推送、远程分支删除及发布标签遵循用户授权，不因本流程自动执行。

示例（本地合并）：

```bash
git switch main
git switch -c feature/ui
# 开发、提交、测试并审查差异
git switch main
git merge feature/ui
git branch -d feature/ui
```

开始工作前确认本地 `main` 与远程状态；存在分叉时先处理，避免覆盖他人提交。已有提交保留历史，不为套用流程而改写已推送的 `main`。

## 版本发布

不是每次合并都需要发布。确定发布版本后，在 `main` 已验证的具体提交上创建版本标签，例如 `v0.2.0`，并记录版本变化及验证边界。标签用于准确定位发布代码；创建和推送标签在明确要求发布时执行。

提交信息及提交粒度要求见 [提交信息规范](commit-message-spec.md)。
