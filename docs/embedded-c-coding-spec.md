# 嵌入式 C 编码规范（推荐性）

| 项 | 内容 |
|---|---|
| 性质 | **推荐性技术规范（非强制）**：给出推荐做法与配套检查手段，不构成强制约束；是否采纳、以何种强度采纳，由使用方自行决定 |
| 状态 | v2.2 / 2026-10-20 |
| 参考基准 | **MISRA C:2012**（含 AMD1、AMD2）；声明口径见 P-9.8 |
| 适用范围 | 通用嵌入式 C 项目：C 源码的命名、格式、注释、语言使用、复杂度、模块接口与工具链；以及纳入版本控制的文档**文件名**（P-2.20） |
| 不适用范围 | 第三方库及非 C 产物，见 §1.2 |
| 采纳方式 | 可整体采纳，也可按项目裁剪后写入自身的编码规范；是否接入自动检查（CI）由各项目决定 |

**推荐用语**

- **应 / 不应**：强烈推荐遵循 / 避免的做法；不采纳时**宜**说明理由（见 §10）。
- **宜 / 不宜**：一般性建议，存在权衡空间（多对应 MISRA 的 Advisory）。
- **评审项**：缺少可靠自动化手段、宜由人工评审关注的条目（见 §9.2 覆盖表）。
- **本规范条款编号**：`M-x.y` 引用 MISRA C:2012 规则 x.y，`D-x` 引用 MISRA 指令 x，`P-n.m` 为本规范自定条款。

**条文效力**

本文件**不复述** MISRA 条文含义。凡标注 `M-x.y` / `D-x` 的条款，**其判定内容以 MISRA C:2012 原文为准**；本文件只给出采纳建议（"哪些条款值得优先自动化"以及"MISRA 未覆盖处的取值"）。两者冲突时以 MISRA 为准。

未列入 §5 的 MISRA 规则同样值得遵守，但本文档不给出逐条自动化建议，可自动化边界见 §9.2 覆盖表。因此**不宜**对外声称"全量符合 MISRA C:2012"，声明口径见 P-9.8。

## 1. 总则

**P-1.1** 本规范**整体以 MISRA C:2012 为合规基准**。

- MISRA 的 **Mandatory / Required** 规则与指令：**应**遵守（验证手段与边界见 §9.2）。
- MISRA 的 **Advisory** 规则：**宜**遵守，不自动检查。
- 迁移到 MISRA C:2023 属于独立评审事项（规则重新编号，需重做映射表），未完成映射前不宜声称"符合 2023"。

**P-1.2** 说明遵循情况时，依据**宜**为三类：**工具报告**（§9）、**例外记录**（§10）与**评审记录**（限于覆盖表中的"评审项"）。**不应**以"编译器没报错""评审时没人提"作为依据。

**P-1.3** 规则集不宜按人、按模块、按开发阶段裁剪，也不宜按目录裁剪：

- **不应**在子目录放置覆盖性配置（`.cppcheck`）来关闭或放宽检查；
- **不应**在 CI 中使用未登记的 `-Wno-*` 关闭告警；
- **不应**使用 `--line-filter`、逐文件白名单等方式规避统计。

确需差异，**宜**按 §10 记录并说明理由。

### 1.1 适用与豁免

**P-1.4** **第三方库及其源码不参与本规范的任何判定**：既不产生问题项，也不计入存量问题基线，不建议为迎合本规范而改名、改格式、补注释。第三方代码通常包括：

- 第三方组件源码（日志库、JSON 解析库、协议栈、RTOS、算法库等，含其头文件与配置）；
- 代码生成器产物、芯片厂商启动代码与 HAL；
- 引入的完整开源栈自身源码。

豁免范围**宜**以机器可读清单固化，供所有检查脚本共用（清单文件的文件名与位置由项目约定，下文以 `spec-exempt.txt` 指代）：

```
spec-exempt.txt        # 每行一个路径 glob（相对仓库根），'#' 起始为注释
third_party/**
vendor/**
<外部引入目录>/**
```

配套建议：

1. 新引入的第三方代码**应**集中存放在独立目录（如 `third_party/`、`vendor/`、`extern/`，具体由项目约定），与自研代码隔离；
2. **宜**为每个第三方组件登记来源、版本、许可证、是否被修改（模板见附录 F）；
3. 检查脚本**应**按清单排除第三方代码（执行方式见 §9.4）。

**P-1.5** 豁免只针对第三方代码自身，**不针对调用方**。自研代码调用第三方接口的部分仍**应**遵循本规范（含返回值检查、缓冲区长度的校验）。

**P-1.6** 与第三方代码**混放目录中的自研部分不享受豁免**：判定标准是"谁写的"，不是"放在哪个目录"。公共/共用目录内的自研代码与业务代码同等要求，这类目录内不建议再新增第三方代码。

**P-1.7** 豁免**失效条件**：第三方文件一旦被自行修改（打补丁、加钩子、改宏），该文件即失去豁免，**应**移出清单并按自研代码要求处理；确需保留修改的，**宜**在第三方登记文档中记录补丁内容与原因，并把被改文件从豁免清单中移除。

### 1.2 不适用范围

**P-1.8** 以下内容不受本规范约束（不评定、不作为检查对象）：

- 第三方库与其源码（见 P-1.4）；
- 非 C 语言产物：汇编（`.s`/`.S`）、链接脚本（`.ld`）、设备树、Kconfig、CMake、构建与运维脚本（`*.sh`/`*.ps1`/`*.py`）；
- 协议/标准原文摘录、数据表等只读资料；
- 仓库根目录的**固定文件名**：`README.md`、`CONTRIBUTING.md`、`AGENTS.md`、`CHANGELOG.md`、`LICENSE`、`SECURITY.md`（平台约定名，不受 P-2.20 约束）。

## 2. 命名规范

### 2.1 总则

**P-2.1** **所有标识符统一使用小写字母 + 下划线（`snake_case`）。**

**P-2.2** **不应**驼峰（`readDataByIdentifier`）、**不应**帕斯卡（`ReadData`）、**不应**大小写混排（`UdsReadDID`）、**不应**中文、空格、连字符 `-`。

**P-2.3** 本规范只有**两类**大小写例外：

1. **宏与枚举常量**：全大写 + 下划线（见 §2.2 表、P-2.11）。
2. **专有名词**：按附录 E 的**位置相关取值**；清单外的词一律全小写。

> 文档文件名的 `kebab-case`（P-2.20）**不是**本条的例外：文档文件名不是标识符，作用域不同，两处规则互不干涉。

**P-2.4** **文件作用域标识符与具有外部链接的标识符**（全局对象、函数、宏、类型、tag）**应**携带模块前缀，且**前缀放在最前面**。理由：`M-5.1` 要求外部标识符在有效前缀内互异（C99 只保证外部标识符前 **31** 个字符有效），前缀放在尾部会导致区分度失效。

局部变量、函数参数、`struct` 成员**不受此条约束**（短名优先，见 P-2.10）。

**P-2.5** 名称**不应**只靠大小写区分。除 C 语言本身外，部分链接器与文件系统对大小写不敏感；`ls`/`dir` 排序也会因此错乱。专有名词写法（§2.5）**同样**不能用于区分两个标识符或两个文件（`lwip_init` 与 `lwIP_init` 不宜并存）。

### 2.2 各元素命名（唯一取值，无备选）

| 元素 | 规则 | 正例 | 反例 |
|---|---|---|---|
| 宏 | 全大写 + 下划线，`模块_语义` | `UDS_MAX_PAYLOAD` | `MaxPayload`、`uds_max` |
| 枚举类型 | 小写 + 下划线，`_t` 结尾 | `ev_phase_t` | `EvPhase` |
| 枚举常量 | 全大写 + 下划线，`模块_语义` | `EV_PHASE_HANDSHAKE` | `evPhaseHandshake` |
| struct / union 类型 | 小写 + 下划线，`_t` 结尾 | `simulator_t` | `Simulator` |
| struct 成员 | 小写 + 下划线 | `frame_len` | `frameLen` |
| 函数 | 小写 + 下划线，`模块_动作_宾语` | `uds_read_did`、`ev_sm_dispatch` | `udsReadDID` |
| 文件名 | 小写 + 下划线，`模块_小模块` | `ev_sm_handlers.c`、`lwip_tcp.c` | `EvSmHandlers.c` |
| **全局变量** | `g_` + 小写（仅限外部链接） | `g_sim_state` | `sim_state`、`gSimState` |
| **静态变量**（文件作用域 `static`、函数内 `static`） | `s_` + 小写 | `s_rx_buf` | `rx_buf`、`g_rx_buf` |
| `static const` 对象 | 按静态变量处理：`s_` + 小写 | `s_u32_max` | `U32_MAX` |
| **非 static 局部变量** | 小写 + 下划线，短 | `idx`、`ret`、`n` | `theIndexOfCurrentElement` |
| 函数参数 | 同局部变量 | `did`、`buf` | `DID` |
| 布尔量 | `is_` / `has_` / `can_` + 语义 | `is_charging`、`has_error` | `charge_flag` |
| 物理量 | **应**带单位后缀，取值见 §2.6 | `wait_bhm_ms`、`voltage_mv` | `wait_time`、`voltage` |
| 指针 | 不加 `p_` 前缀（区分靠命名语义，不靠类型） | `char *buf` | `char *p_buf` |
| **专有名词** | 按附录 E 该位置的唯一写法 | `lwip_tcp.c`（文件名）、`GBT27930_MAX_PAYLOAD`（宏） | `Lwip_tcp.c`、`Gbt27930_max_payload` |

**P-2.6** `_t` 后缀**宜**用于类型别名（含 enum / struct / union / typedef）。注意 `_t` 属 POSIX 保留命名空间（见 P-2.11）：若项目在意纯 MISRA 取向，**宜**整体改用别的后缀（如 `_type`）并一次性记录，而不是逐处解释。第三方库自带的 `_t` 类型不受约束（P-1.4）。

**P-2.7** **不应**用 `typedef` 隐藏指针类型（如 `typedef struct foo *foo_t;`）。指针性**宜**在声明处可见。不透明句柄写法见 P-7.8。

**P-2.8** `g_` 前缀**只宜**用于具有外部链接的全局变量。**不应**给 `static` 变量加 `g_`（这是实践中最常见的漂移）。

**P-2.9** **非 static 的**局部变量、函数参数**不应**使用 `g_` / `s_` 前缀（函数内 `static` 变量按 §2.2 表使用 `s_`）。

**P-2.10** 循环计数等极短名称只**宜**使用 `i` / `j` / `k` / `n` / `idx`。**不应**使用其他单字符名称。

### 2.3 保留标识符与唯一性（MISRA）

**P-2.11** `M-21.1` / `M-21.2`：**不应**使用保留标识符。判定以 MISRA C:2012 原文与 C 标准（未来库方向）为准；工程上高频命中的类别如下：

| 形式 | 建议 | 依据与说明 |
|---|---|---|
| 含 `__`（双下划线） | **不应**使用（任何位置） | 保留给实现，例：`__CRC32_H`、`__WINDOWS__` |
| `_` + 大写字母开头 | **不应**使用 | 例：`_ELOG_CFG_H_` |
| 文件作用域 `_` + 小写开头 | **不应**使用（含宏、tag） | 保留给实现 |
| `E` + 大写字母或数字开头 | **不应**使用 | `errno.h` 保留（`E` + 小写不受限） |
| `is` / `to` + **小写字母**开头 | **不应**使用 | `ctype.h` 保留；`is_charging` 有下划线分隔，不受限 |
| `str` / `mem` / `wcs` + **小写字母**开头 | **不应**使用 | `string.h` / `wchar.h` 保留 |
| `LC_`、`SIG`/`SIG_`、`atomic_`/`memory_order_`、`cnd_`/`mtx_`/`thrd_`/`tss_` 开头 | **不应**使用 | 对应标准库保留 |

> 本表是"高频命中清单"，不是保留名全集；完整判定以 MISRA 原文为准。工具实现与实测覆盖见 §9.1 / §9.2。

**P-2.12** **头文件保护宏宜形如 `模块_文件名_H`，全大写。** 参考算法：

1. 取仓库根到该头文件的相对路径，去掉仓库根与末尾的文件名；
2. 去掉其中纯属存放位置的目录段（如 `inc/`、`src/`、`include/`）与项目约定的公共顶层段（各项目自行约定保留到哪一层）；
3. 剩余目录段与文件名按 `_` 连接；
4. 段内出现附录 E 的专有名词时，按"宏 / 枚举常量"位置替换为登记写法；
5. 末尾追加 `_H`，整体转为大写。

```
<模块目录>/inc/crc32.h            →  <模块目录大写>_CRC32_H
<模块>/<子模块>/include/tp.h      →  <模块>_<子模块>_TP_H
```

**不应**使用 `__XXX_H`、`_XXX_H_`、`XXX_H`（无模块前缀）三种写法；同一仓库内**宜**保持算法一致。

**P-2.13** `M-5.2` / `M-5.3`：同一作用域内标识符**应**互异；**不应**内层作用域遮蔽外层同名标识符（含参数遮蔽全局）。

**P-2.14** `M-5.4` / `M-5.5`：宏名之间、宏名与其他标识符之间**应**互异。

**P-2.15** `M-5.6` / `M-5.7`：`typedef` 名、`tag` 名**应**唯一。

**P-2.16** `M-5.8`：具有外部链接的对象/函数名**应**唯一。`M-5.9`：具有内部链接的**宜**唯一（Advisory，仅记录）。

**P-2.17** 同一命名空间内名称**不宜**仅靠大小写、下划线数量或专有名词写法区分；本条与 `M-5.x` 同源，判定以 `M-5.x` 原文为准。命名一致性要求另见 `D-4.5`（以 MISRA 原文为准）。

### 2.4 文件、目录与仓库命名

**P-2.18** C 源文件与头文件：小写 + 下划线，`模块名_小模块名.h/.c`；**实现文件与头文件同名**。**不应**使用 `-`，**不应**出现 `myFile.c` 这类大小写混排写法。第三方库自带的文件名不受约束（P-1.4）。

**P-2.19** 目录名**宜**全小写 + 下划线（或单个小写单词），并与其中的主要模块同名。本规范**不规定具体目录架构**：模块如何分层、头文件与源文件是否分目录存放、第三方代码放在哪里，都由各项目按自身规模与构建系统决定，只需满足两条：

1. **自研代码与第三方代码在目录上可区分**（便于自动排除，见 §1.1 / §9.4）；
2. **同一职责只有一处存放位置**，避免同名模块分散在多处。

目录结构一旦确定，**宜**写入项目自身的工程说明并从一而终；调整目录影响面较大，**宜**单独提交。

**P-2.20** **文档文件宜使用小写 + 横线（`kebab-case`）。** 适用范围：纳入版本控制的 `.md` 文件，**除** P-1.8 所列根目录固定文件名与豁免清单中的路径。

| 正例 | 反例 |
|---|---|
| `GBT27930-2015-protocol-notes.md` | `GBT27930_2015_协议整理.md` |
| `lwIP-tcp-stack-notes.md` | `LwIP_Tcp_Stack_Notes.md` |
| `getting-started.md` | `快速开始.md` |

- **不应**下划线、空格、中文名；非专有名词部分**不应**大写。
- 文件名中的**专有名词**按附录 E 的"文档文件名"位置取唯一写法（`lwIP-tcp-stack-notes.md`、`GBT27930-2015-protocol-notes.md`），分隔符仍然只用 `-`；这些写法**宜**同时登记到命名白名单文件（见 P-9.7）。
- 文档改名**应**同步更新所有引用点（工程说明、代码注释、README 链接）。

**P-2.21** 仓库名：全小写 + 横线。

**P-2.22** **不应**空格、中文/全角字符、结尾点或空格；**不应** Windows 保留名（`CON`/`PRN`/`AUX`/`NUL`/`COM1`~`COM9`/`LPT1`~`LPT9`）。

### 2.5 专有名词（白名单制）

**P-2.23** 专有名词**不必强行转成全小写**，但**例外只对附录 E 清单内的词、且只在附录 E 登记的位置生效**：清单外的词一律全小写；要用非小写写法**应**先在附录 E 增补登记，并随第一个使用它的 PR 一起提交——**不应**事后补录。第三方库自带的标识符不登记、不判定（P-1.4）。

**P-2.24** 清单按「专有名词 × 使用位置 → 唯一写法」登记。同一位置下，同一名词**只能有一种写法**：登记了 `lwip` 就**不应**再出现 `lwIP`、`LwIP`（注释与文档除外，见附录 E 位置划分）。

**P-2.25** 专有名词**之外**的部分仍**应**全小写 + 下划线。**在标识符位置，专有名词一律取附录 E 登记的小写形式**：

| 位置 | 写法 | 正例 | 反例 |
|---|---|---|---|
| 函数名、变量名、目录名、C 文件名 | 全小写 | `gbt27930_read_data`、`lwip_tcp.c`、`j1939_tp.c` | `GBT27930_read_data`、`gbt27930_readData` |
| 宏、枚举常量 | 全大写 | `GBT27930_MAX_PAYLOAD`、`J1939_TP_TIMEOUT_MS` | `Gbt27930_Max_Payload` |
| 注释、文档正文 | 公认写法 | `GB/T 27930`、`lwIP` | — |
| 文档文件名 | 附录 E 登记写法 | `lwIP-tcp-stack-notes.md` | `lwip_tcp_stack_notes.md` |

**P-2.26** **行业缩写不属于专有名词**，不享受本例外。`UDS`、`CAN`、`CRC`、`DID`、`PGN`、`SPN`、`SOC`、`BMS`、`ECU` 等：

- 在**函数名、变量名、文件名**中一律全小写（`uds_read_did`、`can_send`、`crc32_calc`、`j1939_tp.c`）；
- 在**宏与枚举常量**中写作全大写 + 下划线（`UDS_MAX_PAYLOAD`，见 §2.2 表）；
- 仅在**注释与文档**中按惯用大写书写（UDS、CAN）。

判据：这个词是「这东西本身就叫这个名字」（`lwIP`、`FreeRTOS`、`cJSON`、标准号 `GB/T 27930`）还是「一个普通的行业名词」（UDS、CAN）？只有前者进清单。

### 2.6 物理量单位后缀

**P-2.27** 物理量与时间量**应**使用下表后缀；本表是唯一来源，新增后缀**应**先改本表（随第一个使用它的 PR 提交）。无单位的计数与索引不加后缀（`count`、`idx`、`frame_len`）。

| 量 | 后缀 | 示例 |
|---|---|---|
| 时间 | `_ms` `_us` `_s` | `timeout_ms`、`elapsed_us` |

## 3. 格式（交由工具裁决）

**P-3.1** 格式**不由本文档描述**，**宜**由仓库根目录的 `.clang-format` **唯一裁决**（推荐配置见附录 B）。**不应**以个人偏好为由调整排版；确需调整，**宜**先改配置文件并走评审。

**P-3.2** 正文**不描述排版效果**（"大括号另起一行""指针星号靠哪边"这类自然语言无法穷尽，且与配置一旦不一致就会打架）。要表达格式要求，**宜**写成「意图 → `.clang-format` 键 → 取值」，取值以附录 B 为准：

| 想表达的要求 | `.clang-format` 键 | 取值 |
|---|---|---|
| 缩进 4 空格、不使用 Tab | `IndentWidth` / `TabWidth` / `UseTab` | `4` / `4` / `Never` |
| **所有**大括号另起一行（函数、`if`、`switch`、结构体） | `BreakBeforeBraces` | `Allman` |
| `switch` 的 `case` 缩进一层 | `IndentCaseLabels` | `true` |
| 不自动折行（行宽不设工具上限） | `ColumnLimit` | `0` |
| 指针 `*` 靠变量名（`char *buf`） | `PointerAlignment` | `Right` |
| 强制转换后留空格（`(uint8_t) value`） | `SpaceAfterCStyleCast` | `true` |
| 控制语句与 `(` 之间留空格、函数名后不留 | `SpaceBeforeParens` | `Custom`（本版本等价 `ControlStatements`） |
| 单行 `if` / 短函数不压成一行 | `AllowShortIfStatementsOnASingleLine` / `AllowShortFunctionsOnASingleLine` | `Never` / `None` |
| 不改动注释排版 | `ReflowComments` | `false` |
| 不重排 `#include` | `SortIncludes` | `Never` |
| `#if` / `#define` 不额外缩进 | `IndentPPDirectives` | `None` |

三点约定：

- 风格名（`Allman`、`LLVM` 等）是 `clang-format` 的官方术语，**含义以官方文档为准，本文档不复述**；要看效果就跑一次 `clang-format`，或看附录 B 的配置与示例。
- 上表中 **`SortIncludes`、`AllowShortFunctionsOnASingleLine`、`ReflowComments` 三个键应显式写出**：它们在 LLVM 基础风格里分别默认为"会排序 `#include`""会把短函数压成一行""会重排注释"，省略就会与"不重排、不压行"的要求相反。指针则相反 —— 只要显式写了 `PointerAlignment`，`DerivePointerAlignment` 就不再按文件推导（实测 clang-format 22），无须再写。
- 键值表达不了的排版（空行数量、注释块内部结构、字段对齐取舍）**不写进本章**：前者不作为条款，后者由附录 C 的模板与评审约定（§9.2 覆盖表）。

**P-3.3** 提交前**宜**执行 `clang-format -i`；若接入自动检查，**宜**执行 `clang-format --dry-run -Werror`，不通过即拒绝合入。

**P-3.4** `clang-format` 版本**宜**在开发机与自动检查环境保持一致，并与 `cppcheck` 的版本一起记入 `toolchain.md`（见 P-9.1）。版本不同导致的格式漂移**宜**重跑格式化后修正。

**P-3.5** 行宽**不设**由工具强制的上限（`ColumnLimit: 0`）：工具不自动折行，也不会合并或重排代码里已有的换行。由此两点要注意：① 长行**宜**由评审关注可读性（评审项，见 §9.2），而不是指望工具拦下；中文注释的视觉宽度不另设人工列宽标准；② 一旦决定设硬上限（例如改 `ColumnLimit: 120`），**clang-format 的折行结果即为唯一判定**，正文不必再描述怎么折。

## 4. 注释与可维护性

**P-4.1** `D-4.4`：**宜**不把代码注释掉后留在文件里（该指令为 Advisory，见 P-1.1）。需要保留就删除（版本控制在 git 里）；确需临时屏蔽，**宜**按 §10 记录并注明恢复条件。

**P-4.2** `M-3.1`：**不应**在注释内出现 `/*` 与 `//` 字符序列。`M-3.2`：**不应**用续行符拼接注释。`M-4.2`：**不应**三字符组。

**P-4.3** 每个文件**应**有文件头注释，模板见附录 C.1。

**P-4.4** 每个函数**应**有函数注释块，模板见附录 C.2，至少覆盖：用途、参数、返回值、副作用、并发/重入约束。公共头文件中的函数注释是**接口契约**，不宜省略或写成"见实现"。

**P-4.5** 注释**应**说明"为什么"，不复述"做了什么"。

**P-4.6** 涉及协议实现偏差、非标行为、临时屏蔽的代码，**应**在注释中给出依据（文档章节号或规范条款号）。

**P-4.7** 注释**应**与代码同步：修改行为时同步修改注释与接口契约；失效注释、与代码矛盾的注释**宜**在同一提交内修正。

## 5. 语言使用

本节按 MISRA 的等级给出采纳建议：**Required / Mandatory = 建议纳入自动检查**；**Advisory = 建议人工评审关注**。清单之外的 MISRA 规则同样值得遵守，其可自动化边界见 §9.2。

### 5.1 控制流

| 条款 | MISRA 级别 | 内容 | 建议检查方式 |

| `M-15.5` | Advisory | 函数**宜**在末尾只有一个出口 | 记录（见 P-6.2） |
| `M-15.6` | Required | 迭代/选择语句的语句体**应**是复合语句（花括号不可省） | 自动检查 |

| `M-16.4` | Required | 每个 `switch` **应**有 `default` | 自动检查 |
| `M-16.5` | Required | `default` **应**是第一个或最后一个子句 | 自动检查 |
| `M-16.6` | Required | 每个 `switch` 子句**应**至少含一条语句 | 自动检查 |
| `M-16.7` | Required | `switch` 控制表达式**不应**为布尔本质类型 | 自动检查 |

### 5.4 运行时与输入校验

| 条款 | MISRA 级别 | 内容 |
|---|---|---|
| `D-4.1` | Required | **应**采取措施最小化运行时失效（边界、溢出、除零、空指针） |
| `D-4.7` | Required | 返回错误信息的函数，其错误信息**应**被检查 |
| `D-4.14` | Required | 来自外部来源的值**应**校验有效性 |

**P-5.2** 所有外部输入（通信报文、配置与命令行参数、外部缓冲区）：**应**在解引用/索引前完成长度、范围、枚举合法性校验。校验失败**应**返回错误码（P-5.4），**不应**静默截断或默认放行。

### 5.5 类型模型（落实 `M-10.x` 的取值建议）

**P-5.3**

1. 数值字面量**应**带类型后缀：无符号 `u`（`100u`）、长整型 `l`/`ul`（`1000ul`）；浮点仅允许 `double` 且**应**带小数点（`1.0`）。**不应**依赖默认整型提升。
2. **不应**对有符号类型做位运算与移位；掩码、位域、移位操作数**应**为无符号类型。
3. 不同本质类型之间的赋值与比较**应**显式转换；窄化转换前**应**做范围校验（`D-4.1`）。
4. `char` 仅用于字符/字符串；数值一律用 `uint8_t` / `int8_t` / `uint16_t`…，**不应**用 `char` 存数值。
5. 编译应开启 `-Wconversion -Wsign-conversion`（见 §9.1）；这两组告警的存活即视为本条未落地。

### 5.6 错误处理与资源释放

**P-5.4** 错误码约定：

1. 每个模块定义自己的错误枚举 `xxx_err_t`，`XXX_OK = 0` 表示成功，非 0 即错误；
2. 返回码**应**被检查（`D-4.7`）；确需忽略时**应**写 `(void)` 并给出原因注释；
3. **不应**用魔法返回值（`-1`、`255`）表示错误，**不应**用全局错误变量代替返回值；
4. 校验失败路径**应**返回错误码，**不应**返回默认值继续执行（P-5.2）。

**P-5.5** 不使用 `goto` 时，资源释放**宜**采用以下范式之一，且**应**保证每条错误路径都执行清理：

1. **状态变量 + 单一出口**（推荐，与 P-6.2 一致）：失败路径设置 `err`，末尾按固定的逆序释放；
2. **`do { ... } while (0)` + `break`**：仅用于初始化序列，`break` 视为出口，清理写在循环之后。

```c
static xxx_err_t s_open_ctx(ctx_t *ctx)
{
    xxx_err_t err = XXX_OK;

    err = l1_init(&ctx->l1);
    if (err == XXX_OK)
    {
        err = l2_init(&ctx->l2);
        if (err != XXX_OK)
        {
            l1_deinit(&ctx->l1);   /* 逆序释放已完成的部分 */
        }
    }

    return err;
}
```

### 5.7 断言与不可恢复错误

**P-5.6**

1. **不应**直接使用 `<assert.h>` 的 `assert`；**应**经平台统一封装（如 `osal_assert(cond, msg)` 这类接口；量产平台可编译为陷阱/复位，而不是 `abort`）；
2. 断言表达式**不应**带副作用（`M-13.x`），**不应**把本应执行的语句写进断言；
3. 断言只用于"不可恢复的编程错误"，**不应**用于校验外部输入（那是 P-5.2 的错误码路径）；
4. 发布版本的断言行为**应**在 `toolchain.md` 记录（保留 / 编译为陷阱 / 关闭）。

## 7. 头文件与模块接口

**P-7.1** 头文件保护宏按 P-2.12 推导。

**P-7.2** **不应**在头文件中定义变量或分配存储。例外只有两类：

- `static inline` 函数
- 经评审的 `static const` 只读表（须标注"每翻译单元一份副本"）

**P-7.3** 跨模块共享可变状态**应**通过访问函数（`xxx_get_yyy` / `xxx_set_yyy`）实现；**不应**使用 `extern` 声明可变变量。`extern` 只宜用于只读常量。

**P-7.4** 头文件**应**只包含自身需要的依赖；**不应**使用"万能头文件"（一个头把平台、协议、日志全部拉进来）。

**P-7.5** 每个对外提供接口的 `.c` **应**有同名 `.h`。**不应**把内部实现类型的定义暴露到对外头文件（不透明指针 + 访问函数，写法见 P-7.8）。

**P-7.6** 头文件中的函数名、结构体成员、枚举值一经发布**不应**静默修改；变更**应**在提交说明中标注，标记格式固定为提交正文一行：

```
INTERFACE: <模块>.<符号> <类型: 新增|删除|改名|语义变更>
```

并在 PR 描述中列出兼容性影响。

**P-7.7** 头文件**应**自包含：不依赖包含者先包含其他头文件，`.h` 内的每个 `#include` 都应能被单独编译通过。检查：`check-header-selfcontained.sh`（对每个 `.h` 生成一个只包含它的临时 TU 并编译）。

**P-7.8** 不透明类型推荐写法：`typedef struct xxx_s xxx_t;`（类型本身不是指针，符合 P-2.7），句柄以 `xxx_t *` 传递；对外头文件不宜出现 `struct xxx_s` 的成员定义。

## 8. 分层与平台访问

**P-8.1** 业务层代码**不应**直接操作寄存器、芯片外设或 HAL。硬件访问**应**通过平台抽象层接口（如 `device_open` / `device_read` / `device_write` / `device_ioctl` 这类统一入口）完成。检查脚本：`check-layering.py`（业务层出现寄存器映射符号或 HAL 头文件名即报出，白名单随脚本维护）。

**P-8.2** **不应**在中断/回调上下文调用可能阻塞的接口（锁、动态分配、日志落盘）。共享数据**应**使用平台抽象层提供的原子/锁封装，**不应**用裸 `volatile` 充当同步原语。检查方式：**评审项**（难以静态判定），评审记录**宜**包含 ISR 内的调用清单。

**P-8.3** 字节序**宜**在项目内一次性约定（常见做法：协议层 big-endian，应用层使用主机字节序），并把转换集中封装为统一接口，**不应**在业务代码里散落裸位移/掩码。转换函数名**宜**能看出方向，如 `endian_host_to_be_u16` / `endian_be_to_host_u16`。检查方式：评审项。

**P-8.4** 协议常量（SID、SUB、NRC、PGN、SPN、超时、周期）**应**集中定义在协议类型头文件中，**不应**在业务代码中直接写魔数。

**P-8.5** 安全相关常量（SEED/KEY 算法、CRC 多项式、签名校验值）**应**集中在单一模块，**不应**复制到多处。

**P-8.6** 硬件相关延时、超时、重试次数**应**集中定义（按 P-8.4），**不应**在业务逻辑中写裸数值。

## 9. 工具链与自动检查（建议）

### 9.1 工具清单与免费能力边界

**P-9.1** 若接入自动检查，工具**宜**固定（工具名 + 版本 + 配置文件 + 执行命令）并记入项目的 `toolchain.md`，使开发机与检查环境版本一致。

| 环节 | 工具 | 许可 / 费用 | 能力边界 |

| 命名约定（模块前缀、保护宏） | `cppcheck --addon=namingng.py` | GPL，免费 | 可配置变量/函数前缀、保护宏前缀与大小写，最适合落实 P-2.4 / P-2.12（配置建议见 `namingng.config.json`） |
| MISRA C:2012 | `cppcheck --addon=misra.py` | GPL，免费 | **只覆盖部分规则**；规则文本需自行从 MISRA 获取（`--rule-texts=`）；全量覆盖需商业版（Cppcheck Premium） |

### 9.4 第三方的排除执行

**P-9.4** 所有检查**应**按豁免清单（P-1.4，下文以 `spec-exempt.txt` 指代）排除第三方代码：

1. **cppcheck**：用 `-i` 排除清单中的目录与文件。注意 cppcheck 的 `-i` 对 `#include` 进来的头文件**不生效**（官方文档明确），因此清单**应**同时列出第三方源文件与头文件，头文件侧还需 `--suppress` 或 `--file-filter` 兜底。
2. **统计**：先过滤清单再计数；豁免文件**既不参与检查也不计入基线**。
3. **守卫**：`check-exempt-guard.py` 检查报告中是否出现清单内路径，出现即报错——既防"漏排除"，也防"用豁免洗白自研代码"。

```sh
# run-cppcheck.sh（示意）：按豁免清单生成 -i 参数
exec cppcheck --project=<构建目录>/compile_commands.json \
  --std=c99 --platform=unix32 \
  --enable=warning,style,performance,portability \
  --addon=misra.json \
  --suppress-xml=cppcheck-suppressions.xml \
  "$(sed -e '/^[[:space:]]*#/d' -e '/^[[:space:]]*$/d' -e 's/^/-i/' spec-exempt.txt)" \
  -i <第三方目录> \
  2> cppcheck-results.xml
```

（`--check-level=exhaustive` **宜**留给定期/每日构建；`--library=<平台>.cfg` 按目标平台启用，cppcheck 自带若干平台与库描述文件。）

### 9.7 文档命名校验

**P-9.7** 校验逻辑**宜只有一份实现**：`check_doc_names.py`；`check-doc-names.sh` 与 `.ps1` 只做薄包装（避免两份逻辑漂移）。要求：

1. 校验范围：`git ls-files '*.md'`（纳入版本控制的全部 Markdown），**不是**只扫文档目录；
2. 排除：P-1.8 的根目录固定文件名、`spec-exempt.txt` 中的路径；
3. 合法名 = `^[a-z0-9][a-z0-9.-]*\.md$`，或命中 `doc-name-allowlist.txt` 中的登记正则（附录 E 的文档文件名写法，如 `^GBT27930-`、`^lwIP-`）；
4. 输出**全部**不符合项后再失败（不遇错即退）。

```python
#!/usr/bin/env python3
"""校验纳入版本控制的 Markdown 文件名（P-2.20 + 附录 E）。"""
import fnmatch
import re
import subprocess
import sys
from pathlib import Path

FIXED = {"README.md", "CONTRIBUTING.md", "AGENTS.md",
         "CHANGELOG.md", "LICENSE", "SECURITY.md"}
KEBAB = re.compile(r"^[a-z0-9][a-z0-9.-]*\.md$")


def read_lines(path):
    p = Path(path)
    if not p.is_file():
        return []
    return [ln.strip() for ln in p.read_text(encoding="utf-8").splitlines()
            if ln.strip() and not ln.lstrip().startswith("#")]


def main():
    # 两个清单的文件名/位置按项目约定调整
    exempt = read_lines("spec-exempt.txt")
    allow = [re.compile(p) for p in read_lines("doc-name-allowlist.txt")]
    files = subprocess.run(["git", "ls-files", "*.md"], capture_output=True,
                           text=True, check=True).stdout.split()
    bad = []
    for f in files:
        base = Path(f).name
        if base in FIXED or any(fnmatch.fnmatch(f, p) for p in exempt):
            continue
        if KEBAB.match(base) or any(rx.search(base) for rx in allow):
            continue
        bad.append(f)
    for f in bad:
        print(f"文件名宜为 kebab-case 或附录 E 登记写法：{f}")
    return 1 if bad else 0


if __name__ == "__main__":
    sys.exit(main())
```
