# 提交信息规范（推荐）

| 项 | 内容 |
|---|---|
| 名称 | 提交信息规范 |
| 状态 | v1.0 / 2026-10-20 |
| 性质 | 推荐性技术规范（非强制） |
| 参考基准 | Conventional Commits v1.0.0；Pro Git 的提交信息守则 |
| 适用对象 | 使用 Git 的仓库（不限语言、平台与项目类型） |
| 采纳方式 | 可整体采纳，也可只取 §1 的部分条款；是否接入自动检查（§3）由项目决定 |

**推荐用语**：**应** / **不应** 表示强烈推荐（不这么做**宜**在评审中说明理由）；**宜** / **不宜** 表示一般建议，可按项目情况取舍；**评审项** 表示目前没有可靠的自动检查手段、只能靠人工关注。条款编号为 `P-<章>.<序>`。

本文件只给采纳建议，不构成强制约束。与项目既有提交约定冲突时以项目约定为准，差异**宜**记入项目的工程说明。若项目同时采纳《嵌入式 C 编码规范》，可把该规范自检清单里的提交信息一项指向本文件。

## 1. 条款

**P-1.1** 提交标题**宜**采用 Conventional Commits 的固定形式：`<type>(<scope>): <summary>`。`<scope>` 可选，写受影响的模块或子系统；`<summary>` 用中文或英文**均**可，同一仓库**宜**统一。

**P-1.2** `<type>` **宜**从下表取。判断依据是**这次改动的性质，不是改了什么文件**：

| type | 含义 | 判断口径 |
|---|---|---|
| `feat` | 新增功能 | 使用方能感知到的新能力、新接口、新配置项 |
| `fix` | 修缺陷 | 修正了错误行为（含崩溃、越界、时序错误） |
| `perf` | 性能 | 行为不变，耗时 / 内存 / 体积下降 |
| `refactor` | 重构 | 行为不变，结构或命名改变 |
| `docs` | 文档 | 只动文档与注释（含文件头、函数注释块） |
| `test` | 测试 | 只动测试代码与测试用例 |
| `build` | 构建 / 依赖 | 构建脚本、工具链版本、第三方依赖升级 |
| `ci` | 流水线 | CI 配置与检查脚本 |
| `style` | 纯格式 | 只动空白、换行、排版（不改语义） |
| `revert` | 回滚 | 回滚既有提交 |
| `chore` | 杂项 | 以上都不是（版本号、生成物、仓库配置） |

**P-1.3** 破坏性变更**应**在 `type`（或 `scope`）后加 `!`，并在正文用 `BREAKING CHANGE: <说明>` 交代影响面与迁移做法；只加 `!` 而不说明影响面**不宜**视为完整。

**P-1.4** 标题**宜**简短、用陈述或祈使口径、结尾不加句号，中文**宜**控制在 50 字以内；标题与正文之间**应**空一行；正文**宜**说明"为什么改"与影响面，"怎么改"交给 diff。

**P-1.5** 涉及已发布接口（头文件符号、公共 API、配置键、命令行参数）时，正文**应**带一行 `INTERFACE: <模块>.<符号> <类型>`，说明变更对象与类型；该标记与《嵌入式 C 编码规范》的 P-7.6 一致。

**P-1.6** 有关联问题单时**宜**写在正文末尾：`Fixes #123` / `Closes #123`（**不宜**塞进标题）；**没有对应问题单时整行省略**，**不宜**写 `Fixes #000`、`N/A` 之类的占位。要求签署来源的仓库**应**带 `Signed-off-by:`。自定义 trailer（例如标注 AI 参与、结对作者）**宜**用 `-` 替代空格（如 `AI-Claude: yes`），或直接写进正文段落。

**P-1.7** 一次提交**宜**围绕一个独立功能、缺陷修复或有意义的开发阶段，完成并验证后提交。同一任务内的多次编辑、修补、必要格式化和测试调整可以合并，无需每次小改动或每轮对话立即提交。独立缺陷或具有独立验证价值的阶段成果可单独提交；用户明确要求提交或暂不提交时，按用户要求执行。

提交前**应**检查差异，避免混入无关改动。与功能无关的大范围格式化**宜**单独提交，本次修改所需的格式化可随功能提交；回滚**宜**用 `revert` 而不是手动改回。

**P-1.8** 若接入自动检查，**宜**用 `commitlint` 加提交钩子（或 CI 检查点）只校验**标题与 footer 的形态**，不校验 `<summary>` 的措辞；`<type>` 的允许值**宜**在钩子配置、提交模板与本文件 §1 三处保持一致。

## 2. 示例

正例：

```
feat(bms): 增加 SOC 低电量预警

阈值从配置读取，默认 15%，低于阈值置位状态并触发一次上报。
原实现只在充电时判断，放电需到 5% 才报，现场出现过深度放电。

INTERFACE: bms.alert_cfg bms_alert_cfg_t
Fixes #482                                  ← 无对应 issue 时整行删除；只完成一部分工作改用 Refs #482
```

```
fix(flash): 修复跨扇区写入丢尾字节

擦写地址未按页对齐时，末页剩余长度少算 1 字节。
```

> 第 2 个示例没有关联 issue，正文最后一行就是结尾 —— **没有 issue 就不写这一行**，也不必用 `N/A` 占位。

```
refactor(log)!: 统一日志接口为 osal_log_write

旧宏 LOG_* 全部移除，改用 osal_log_write(level, fmt, ...)。
迁移：替换宏调用即可，等级常量由 LOG_LEVEL_* 改为 OSAL_LOG_*。

BREAKING CHANGE: LOG_* 宏不再提供，外部模块需一并替换。
```

**不宜**的写法：

```
update                                   ← 无 type、无信息量
fix: 修改了一下代码，优化了逻辑（详见 diff）   ← "详见 diff" 等于没写正文
feat: 改格式并加了新功能                    ← 一次提交做了两件事
Feat(API): Added new api.                ← type 大小写、过去式、结尾句号
```

## 3. 自动检查（可选）

```js
// commitlint.config.cjs（示意；只校验形态，不管措辞）
module.exports = {
  extends: ['@commitlint/config-conventional'],
  rules: {
    'type-enum': [2, 'always', ['feat', 'fix', 'perf', 'refactor', 'docs',
      'test', 'build', 'ci', 'style', 'revert', 'chore']],
    'header-max-length': [2, 'always', 72],   // 标题硬上限
    'subject-empty': [2, 'never'],
    'subject-case': [0],                      // 关掉：中文 summary 会被误判大小写
    'body-max-line-length': [1, 'always', 100],
  },
};
```

```sh
# 提交钩子（一次配置）
npx husky add .husky/commit-msg 'npx --no -- commitlint --edit "$1"'
# CI 检查点：只校验本次分支新增的提交
npx commitlint --from origin/main --to HEAD
```

要点：`subject-case` **宜**关闭（中文标题会被默认规则误判大小写）；`header-max-length` **宜**用 72 而不是 commitlint 默认的 100；自动检查只判形态，措辞好坏留给人评审。

## 4. 提交前自检清单

- [ ] 标题符合 `<type>(<scope>): <summary>`，`<type>` 取自 P-1.2 表
- [ ] 标题结尾无句号，长度不超 72 字符（中文**宜** ≤50 字）
- [ ] 标题与正文之间空一行；正文写了"为什么改"与影响面
- [ ] 破坏性变更：标题带 `!`，正文有 `BREAKING CHANGE:`
- [ ] 有接口变更时正文带 `INTERFACE:` 行
- [ ] 有关联问题单时写了 `Fixes #N` / `Closes #N`；没有则整行省略
- [ ] 提交围绕完整功能、独立修复或可验证阶段，没有混入无关改动及大范围格式化
- [ ] `git log --oneline -5` 回看，标题脱离 diff 也能读懂

## 附录 A 与其他提交约定的关系

| 约定 | 形态 | 与本文档的关系 |
|---|---|---|
| Conventional Commits v1.0.0 | `<type>(<scope>): <summary>` + `!` / `BREAKING CHANGE:` | 本文档的基础，有官方简体中文版 |
| Angular 提交约定 | 同形态，`<type>` 更少、`<scope>` 必填 | Conventional Commits 的前身；只取形态、不取必填 scope |
| Pro Git 守则 | 空行分隔、标题 ≤50 字、祈使句、说明"为什么" | P-1.4 与之一致 |
| Linux 内核风格 | `subsystem: summary` + `Fixes:` / `Reported-by:` / `Signed-off-by:` | 无 `type` 前缀；其 footer 用法与 P-1.6 相通 |
| gitmoji | `:emoji: summary` | 机器可读性弱，本文档不采用 |
| Gerrit / DCO | `Change-Id:` / `Signed-off-by:` | 按仓库要求附加，见 P-1.6 |

配套工具：`commitlint`（校验形态）、`husky`（提交钩子）、`commitizen`（交互式生成）、`gitlint`、`conform`；变更日志可用 `semantic-release`、`release-please`、`git-cliff` 从提交信息自动生成。
